## Controllers that are detected but never read (#61, related #155)

ncarson9's log for the 8BitDo GameCube mod kit in Android mode shows, in order:

```
09:47:39.119 [pad] 578 controller mappings from ...\BlueWake\gamecontrollerdb.txt
09:47:40.105 [aurora:info:aurora::input] Added controller '8BitDo GameCube' (instance 5, vid 2dc8, pid 286a, type 1)
```

So the mapping loads and the controller is opened, yet the game gets no input. The source explains why:

- SDL gives a joystick a player index only when it is detected, and only if it is already a gamepad
  then (`SDL_PrivateJoystickAdded`: `if (player_index < 0 && SDL_IsGamepad(instance_id))`).
  SDL's built-in database has no entry for `2dc8:286a`.
- BlueWake loads `gamecontrollerdb.txt` (`runtime/host/src/mouse_camera.c`) after Aurora has started
  SDL. When the new mapping turns the already-detected joystick into a gamepad, SDL sends
  `SDL_EVENT_GAMEPAD_ADDED` from its mapping-change path, which assigns no player index.
- Aurora reads a port's controller by player index (`get_controller_for_player`). Its fallback that
  would take "the first unassigned controller" is compiled out (`#if 0` in `aurora/lib/input.cpp`), and
  `apply_port_preferences` returns at once when no port preference was ever saved.
- BlueWake never calls `PADSetPortForIndex`, so neither menu can assign a controller to player 1.

Expected workaround, not yet confirmed by the reporter: connect the controller after BlueWake has
started, so SDL detects it with the mapping already loaded. Fix: set `SDL_GAMECONTROLLERCONFIG_FILE`
before SDL starts, give a connected gamepad without a player index the first free port, and add a
controller picker (requested in #155). #155 (Mayflash adapter) has no platform, mode or log yet. SDL's
built-in database does know the adapter's PC mode (`0079:1843`, `0079:1844`), which shows up as one
controller per adapter port, so it may be a different case: for example a controller in another port
than the one holding player 1.

## Baton left and right reversed (#156)

The reporter says "the horizontal controls of the wind waker are inverted for the right stick" in 0.5.0.
`bluewake_mouse_camera_pad` (`mouse_camera.c`) negates the C-stick's X whenever the fast right-stick
camera is on but neither owns the view nor aims, and the stick is tilted. That is the swimming/boat/
targeting fix from [#44](https://github.com/chrissotraidis/bluewake/pull/44), which is in 0.5.0 and not
in 0.4.0. Conducting with the baton uses the C-stick and is not one of the stick camera's own modes,
so the flip would mirror the song directions. The setting defaults on for Windows and the Mac. This
fits the report; the reporter has been asked to confirm it is the baton. Fix: restrict the flip to the
game's camera styles that turn the view. Workaround: Fast right-stick camera off.

## Stick dead zone (#138)

Confirmed per axis: `pad.cpp` zeroes `xl` and `yl` separately below `stickDeadZone`, then divides by
256 without rescaling, so small diagonals snap to an axis. The same block skips the cutoff when
`m_deadZones.useDeadzones` is false, and the host can reach that through `PADGetDeadZones(port)`, so a
fix may need no RecompCore change. The guest's own clamp then applies the GameCube dead zone.
