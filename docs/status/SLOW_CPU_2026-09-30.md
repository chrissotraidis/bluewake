# A slower CPU: the GX worker at 14,000 draws a frame — 2026-09-30

A tester with a Ryzen 5 5600X and a GeForce RTX 3060 reported about 25 frames a second from the Windows
release (0.1.0). Every Windows measurement until then was on one PC, an i9-13900KF, whose performance cores
are much faster one thread at a time than a Zen 3 core. The game is one CPU's worth of translated code on
one thread, and the GX translation worker that turns its FIFO into draws is another single thread the game
waits for at every frame's end, so the speed of one core is what matters, not the number of cores.

## Reproducing it without the PC

The i9-13900KF's efficiency cores (Gracemont, about 4.3 GHz) are slower one thread at a time than a Zen 3
core, and its performance cores are faster. Pinning BlueWake to 12 of the E-cores (process affinity
`0x0FFF0000`) is a harsher stand-in for a 5600X; pinning it to 6 P-cores with their hyperthreads
(`0xFFF`) has the 5600X's thread count at a faster core. The route: load the Outset save and stand at the
spawn view (about 14,400 draws a game frame, the heaviest view of the route), then run and turn (the pad
script's stick form from retrace 1500). Paced like a player, the release's defaults (Smooth Motion 60),
windowed, the display at 60 Hz.

| Release 0.1.0 | Standing at the spawn view | Running |
| --- | --- | --- |
| all 32 threads | 30 game / 60 shown | 30 / 60 |
| 6 P-cores + HT | 30 / 60 | 30 / 60 |
| 12 E-cores | 23-26 game / 46-52 shown, the game waiting 190-250 ms a second for the GX worker | 26-27 / 52-55 |
| 12 E-cores, Smooth Motion off | 27 | 30 |

So the count of cores is not the problem; the speed of one is. The release's `[fps-dip]` lines on the
E-cores read `reason=game below full speed` with `waits: gx=221ms` and more, which is what a tester's log
should show if this is their problem.

## Where the time went

Sampled on the E-cores at the spawn view (the thread sampler, symbolized with the app's PDB):

- The game thread: 69 percent busy, 24 percent of its samples blocked in the drain at `GXSetDrawDone` (the
  host's draw-done barrier, `runtime/host/src/main.c`, waits for the worker to translate the whole frame).
- The GX worker: only 66 percent busy. The two threads mostly took turns: the worker idles while the game
  runs its logic, and the game waits while the worker translates the frame's last draws.
- Inside the worker, nothing dominated: building each draw's plan (13 percent), memcpy and memcmp (about 21
  percent: the 2.3 KB transform snapshot copied three times, the 2.8 KB constant block copied into Smooth
  Motion's job and compared with the draw before's), Smooth Motion's hand-off (a sequentially consistent
  store and load per draw, about 4 percent), a validation-only pass over every vertex (about 2 percent),
  heap allocations and locks (about 8 percent: a `std::function` holding a copy of the pipeline config at
  every draw, the sampler, bind group and layout caches' locks) and address resolution (about 5 percent).

## Changes (RecompCore GXRuntime; the app only, the game module is unchanged)

| Change | Where |
| --- | --- |
| The pipeline state derived from the BP, CP and XF registers cached by a register version, not rebuilt at every draw (ported from `native-60hz-pc` dc81247 and f863821; the host's draw tag registers leave the version alone, so particles hit too), and the vertex walk cached by its VCD/VAT: 96 percent hits | `gxcore/src/gxcore.cpp`, `gxcore.hpp` |
| The assembly totals (a walk over every vertex's indices) only in the sinks whose totals something reads, not the gxcore renderer's | `frontend/src/render_sink.cpp`, `render_sink.hpp` |
| A draw's pipeline lookup remembered for the draw after it (one entry for the colour and one for the early-depth pipeline) until the pipeline cache is shut down: no `std::function`, no hash, no lock | `aurora/lib/gfx/common.cpp`, `pipeline_cache.cpp` |
| A draw's texture bind group remembered for the next draw with the same view and sampler, within a frame: no layout, sampler or bind group lock | `aurora/lib/gfx/gxcore_draw.cpp` |
| Smooth Motion's job hand-off: a draw whose constants repeat the job before's leaves the 2.8 KB copy to the helper (which keeps the last it was given), and the sequentially consistent fence is paid only when the helper may be asleep | `aurora/lib/gfx/gxcore_draw.cpp` |

Measured the same way (E-cores, paced, Smooth Motion 60):

| | Standing at the spawn view | Game waiting for the GX worker | Running |
| --- | --- | --- | --- |
| Release 0.1.0 | 23-26 game frames a second | 190-250 ms a second | 26-27 |
| These changes | 29-30 | 20-65 ms a second | 30 |

Unpaced with Smooth Motion off (the most the E-cores can run the game there): 29.7 game frames a second
before, 33.4-34.4 after, with the game thread (92-95 percent busy) the limit instead of the worker (65-75
percent busy).

### Verified exact

Deterministic captures (`BLUEWAKE_CAPTURE_OPENING_FRAME`, `_RETRACE`, `_INTERVAL`) of the same route,
unpaced with Smooth Motion off, the window's size pinned (`window=` in the run's settings: the default comes
from the display) and `mouse_camera=0` (a real mouse over the test window turns the camera without counting
as live pad input, and one run differed for that alone): the release twice gives the same 19 frame hashes (retraces 803 to 2641),
and these changes give the same 19. With Smooth Motion at 60, paced, the in-between frame dumps
(`DOL_AURORA_FRAME_INTERP_DUMP`, game frames 880-910, Link running and turning): all 62 images (31 real,
31 in-between) byte for byte the release's.

The whole new-game opening (the title, a new file, the prologue's cutscenes, Outset to the lookout) cannot be
compared frame for frame: when a capture or a game-frame number lands depends on the host's timing there,
and the release differs from itself (by retrace, 55 of 57 captures the same). Where two runs captured the
same retrace, these changes matched the release 54 of 54. For the cache itself there is a check that timing
cannot move: `DOL_GXCORE_DERIVED_VERIFY=1` derives the state again at every hit and compares it with the
cached state. Through the whole opening: 34,851,442 hits verified, 0 mismatches.

## Tried and dropped: a submission thread

The worker split in two, the FIFO parse and the plans on one thread and Aurora's recording and the
presents on another (a queue of plans between them, the recording lock and the display-copy present taken
by the second). Exact (the same 19 hashes and 62 images), but no faster: unpaced, 32.2-32.8 game frames a
second against 33.7 without it (the same exe, `DOL_GX_SUBMIT_THREAD=0`), and the two threads used 20 to 30
percent more CPU together than the one: each draw's plan (about 4 KB with its vertices) crossed from one
core's cache to the other's. On a 6-core CPU with SMT that is CPU the game thread shares. The patch is kept
outside the tree; the plan would need to shrink a great deal before it pays.

## Diagnostics added (for testers' logs)

- `[fps] ... busy: gx=N% interp=N% render=N%`: how busy the GX worker, Smooth Motion's helper and the render
  worker were that second. One near 100 percent is the thread a slower CPU runs out of.
- `[fps-dip] ... threads: gx=N% interp=N%`: the same in each dip line.
- `[present-slow] present=N ms=... lock=... end_frame=... events=... begin_frame=...`: a present that held
  the game thread 100 ms or more, and which part took the time; `[events-slow] pump=... host=... last=...`
  splits a slow event pump into SDL's own pump and the host's handlers, with the last event's type.
- `CPU model:` now from CPUID, so it no longer reads `Unknown` after the first launch's disc picker (the
  file dialog set up COM security first and the WMI query failed), and a new `CPU cores:` line (for example
  `6 cores, 12 threads`, or `24 cores (8 performance, 16 efficiency), 32 threads`).

## Occasional freezes: the window's event pump

About one run in five on this PC froze the game for 0.4 to 1.2 seconds, in the release as much as with these
changes. The new lines put all of it in the present's `events` part, and in SDL's pump rather than the
host's handlers (`[events-slow] pump=925 ms host=0 ms ... last=0x204`, `SDL_EVENT_WINDOW_EXPOSED`). A sampler
watching the game thread caught one: 299 of its 378 samples in `NtUserMessageCall` under `USER32`,
`uxtheme` and SDL's pump - a message sent to another thread's window and waited for. When BlueWake's window
becomes active, Windows tells the window losing activation, in whichever program owns it, and waits for its
answer; SDL pumps window messages on the thread that made the window, which is the game thread. On this PC
the other program was a busy one (the tools driving the tests), so the freeze depends on what else is
running, not on BlueWake's own work. Startup's slower parts here are Direct3D's setup and the display-mode
list (`NtUserEnumDisplaySettings`, slow with this PC's several virtual displays).

## What to ask a tester for

The newest `%APPDATA%\BlueWake\logs\session-*.log` after a minute of play on Outset, and what F9 reads.
Look at the `CPU model`/`CPU cores` lines, then the `[fps-dip]` lines: `reason=game below full speed` with a
large `waits: gx=` is the worker (and `threads: gx=` near 100 percent); large `present=` or `gpu=` is the
display or the GPU; `busy=` near 100 percent with small waits is the game thread itself.

## Next

- The game thread is now the limit on the slowest cores: about 80 percent of it is translated game code.
  Native versions of measured hot functions (collision, J3D animation, math leaves), verified against the
  translation byte for byte, are the path (`docs/status/RECOVERED_J3D_2026-09-30.md` and the natives work).
- The worker still copies the 2.3 KB transform snapshot three times a draw and rebuilds and compares the
  2.8 KB constant block; versioning the XF state (as the register version above) would let an unchanged
  draw skip all of it.
- A `GXSetDrawDone` that commits the PE finish when the worker reaches it, instead of draining, would let
  the game's next frame overlap the translation's tail; it changes when the game sees the GPU finish and
  where the present happens, so it needs its own verification.
