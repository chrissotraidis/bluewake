## Windows builder and the app profile (#153)

The committed `windows/pgo/app.profdata` was recorded with clang 22. The builder now runs the same toolchain's
`llvm-profdata show` on it first and builds the app without it, with a note, when that fails. With the real
profile on this Mac, LLVM 18 and 20 print the reporter's exact error and skip it, LLVM 22 uses it, and
compiling with `-fprofile-instr-use` reproduces the reported failure with clang 20. The first unit test ran a
shell script as `llvm-profdata.exe`, which Windows CI cannot execute; it now mocks the call.

## Controllers and player 1 (#61)

Cause in the October 7 triage. `bw_claim_player_one` (`controller_ports.h`) runs when a controller is added,
removed or remapped: with nobody on player 1, the first connected controller takes it through SDL's player
index. It is not saved: Aurora's `PADSetPortForIndex` saves a preference, and `apply_port_preferences` then
keeps any other controller off that port. `tests/desktop_controller_test.cpp` reproduces the report with real
SDL and Aurora: a virtual joystick of unknown type, then a mapping line, becomes a gamepad with no player
index and port 0 empty; after the claim its A press reaches `PADRead`. A controller already on player 1 is
never displaced; a player-2 controller takes player 1 when the first is unplugged. #155 (Mayflash in PC
mode, one device per adapter port) may need a controller picker and is waiting on the reporter's log.

## The Wind Waker baton (#156)

#44's flip of the C-stick's X, for the game's own camera, applied whenever the fast stick camera was not
driving the view. Conducting starts an event camera, so it applied there too. The flip is now skipped while
`daPyStts1_WIND_WAKER_CONDUCT_e` is set: bit 0x1 of `mPlayerStatus[0][1]` at `0x803CA8D4`. The translated USA
code confirms the address: `procTactWait_init` at `8014DF4C..5C` ORs 1 into `0x803C4C08 + 0x5CCC`. In a live Mac run
on a copy of a Windfall save, with the Wind Waker put on X by the test-only `BLUEWAKE_MOUSE_TEST_ITEM=0x22`, the
trace showed `conduct=1` from the X press (retrace 910, camera `EN00`, `event=3`) until B (1202), and 0 elsewhere.

## The left stick (#138)

RecompCore patch 0159: with Aurora's cutoff off, `gamecube_axis` scales a stick's full travel to 100, about where
a GameCube stick's gate stops it and what the touch stick sends. The host turns the cutoff off for player 1's
controller after loading any saved mapping (`bw_game_dead_zone`), on desktop and in the iPhone and iPad app.
The game's own clamp (15, full at 87) is then the only dead zone. The test reproduces the report with the
cutoff on (7000 gives 0, 8001 gives 31), then checks 7000 → 21, half → 50, full → ±100, up → +100 and the
C-stick. Built against the unchanged runtime it fails at 21 (27). The Windows CI compiled RecompCore `07559ca`.

## Performance findings

A 10-second `sample` of the Mac host at the title flyover (`sea_T`, about 20,000 draws a frame in #137's log) with
Smooth Motion at 120: of the busy samples, the translated game code had 5,561 and the host's per-block
`host_chassis_requires_full` and `host_chassis_edge_service` about 670, with `chassis_dispatch` another 210.
That path is already reduced to loads and compares; what remains is the number of block boundaries.

The Windows builder's default preparation, run on a copy of this Mac's source (digest `54f54434…`, the same as
Windows), makes 197,458 prepaid block copies in 812 chunks, but only 8,806 guest memory accesses fall inside
them and none has a deadline check. Elliott Tate's `lean_memory.py` then changes 0 accesses, and
`native_entries.py` certifies 0 of 15. BlueWake's `fast_blocks.py` leaves every block with a deadline refund
as it is, which is nearly every block that touches memory. Elliott's version (443,166 blocks) passed 30,000
function comparisons but failed BlueWake's strict boot-route comparison on October 2 (final PC `80324DC0` versus
`80324D68`, 22 of 600 guest-state samples), so it was not adopted
([evidence](FORK_RECONCILIATION_EVIDENCE_2026-10-02.md#generic-prepaid-block-qualification)). Prepaid copies of
memory blocks with lean loads and stores are the largest game-thread change Elliott's builds have and the Windows
release does not. He measured 26.3 to 23.6 ms of game-thread time a frame on a four-core stand-in for that and the
inlined accesses together (PERFORMANCE_OPTIMIZATIONS.md #29); BlueWake already has the inlining, so the part left is
smaller and not yet measured on its own. The next step is to find which block forms cause the divergence, chunk by
chunk, so the safe ones can be copied, then measure that on Windows.
